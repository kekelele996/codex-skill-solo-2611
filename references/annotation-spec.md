# 26.11 领域专项规范摘要

原文：`../official-specs/CC_Codex_用户反馈标注说明_26.11.md`。有出入时以原文为准。

## 数据形态

- 单轮 pointwise：一个 session 只发一次提示词，作为一个容器机会、一条数据；模型结构中断时，允许在同一
  session 内由人工发送字面 `继续`，最多 2 次，多轮共同构成这一条数据。
- 全程 `auto` 模型，`CLAUDE_CODE_MAX_CONTEXT_TOKENS=1000000`，不改模型和上下文配置。
- 一个 session 只提交一次初始快照。模型改动由轨迹承载；运行后仍要保留产物快照供复核。
- 只有结构异常才按 v4 R3–R4 处理：API/网关错误、无 `end_turn`、空回复、悬空工具调用、上下文耗尽，
  或最终回复明确提问/许诺尚未执行的动作。正常 `end_turn` 且没有这些信号时就是完成，不得发送“继续”；
  回复正文正常描述 `interrupted`、中断状态或重试机制，不算实际中断。需要继续时最多 2 次，
  继续用尽后终止并换题，不恢复快照、不换容器、不整题重跑。

## 本期方向

默认「数据工程 / 数仓与数据湖」。任务可以进入下列任一领域的任一子方向，应优先继承真实工程的标签分类：

- 安全：漏洞检测与攻防、身份认证、网络与通信安全、系统安全、其他。
- 游戏、图形与多媒体：音视频处理、图形渲染、游戏开发、图像处理。
- 数据工程：数据采集、爬虫与 RPA、数仓与数据湖、数据分析与数据应用。

SOLO2 账号只允许一个大类，子方向不锁。任务、提示词和提交必须使用配置项
`submission.lockedDomain` 中的账号大类，不能为本单临时改写；如果工程无法真实匹配该大类的
任一合法子方向，应拒绝提交。领域选项是否出现与账号是否锁定无关，跨大类记录会被质检规则 L1 打回。

数据工程真实项目可以横跨采集、清洗、ETL、异构集成、同步、回填、质量隔离、血缘、分析或对账，但不能做成通用后台、CSV 看板或静态爬虫演示。

## 提交表字段

顺序固定 19 列：

1. User Prompt
2. 所属领域
3. 子方向
4. 任务类型
5. 任务难度
6. 语言/框架
7. Harness
8. Harness 版本
9. 操作系统
10. 环境可复现等级
11. 初始环境快照
12. SessionID
13. TurnID/PromptID
14. 轨迹文件
15. 产物快照
16. 运行录屏
17. 交付完整性
18. Feedback
19. 备注

「备注」默认留空，也不进入 API payload。发生 1–2 次继续时，交付表和平台备注写
`模型运行中途中断，人工输入"继续"N次后完成`。提交前扫描最终主会话轨迹发现明文 API Key
暴露风险时，再接中文分号追加 `轨迹中有存在明文apikey暴露风险`。不得写 Key 原文；
其他环境问题、运行过程和异常处理仍留在任务审计材料中。

## 评分与 Feedback

- 交付完整性 1–5 整数，只判断需求是否完整、代码能否运行、有无虚假成功。
  高质量完成的常规上限是 `4`；`5` 是例外档，必须通过
  `references/score-calibration.md` 和 `monitor/score-review.json` 的严格满分审计。
  存在已知缺口、未覆盖边界、未固化回归或只完成正常路径时不得给 `5`。
- Feedback 必须同时分析过程与产物。4–5 分也要写逐项核对的需求、运行结果和过程表现。
- 每个问题写清触发节点、模型实际行为、客观结果和业务影响；用文件名、函数、命令、接口状态、报错或前后计数作证据。
- 测试证据只写与题目业务目标直接相关的测试文件和场景，不写总套件通过数，也不拿无关检查充数。
- 读取、写入、忽略、拒绝等计数必须解释业务含义，不能只列一串没有上下文的数字。
- AI 可以基于轨迹与产物形成结论，但结论必须验证，文案必须自然、通顺、无模板腔。标注专家负责最终复核。
- 不写网络、网关、宿主机权限等外部工程故障对模型能力的评价。
- Feedback 只写产品实现、需求行为和用户可见结果，不暴露模型、容器、临时依赖、本地脚本、
  录屏过程、终端、浏览器、提交、质检、返修、SessionID、PromptID、轨迹等运行流程信息。

## 难度

只收「困难」「地狱」，禁止简单与中等。困难至少满足多模块整合、关键设计取舍、复杂技术关注点中的两项，并且必须有关键设计取舍或复杂技术关注点之一。地狱三项全满足，另需开放方案、隐蔽约束、架构级取舍或深水调试证据。

只在既有页面加视图、字段、筛选、结果表或一个处理步骤，不能凭文件数或步骤数自称困难。详细门禁见 `prompt-standard.md` 和 `difficulty-standard.md`。

## 录屏

录产物真实运行；从干净状态开始，失败也录。720p、mp4、不超过 90 秒，不剪失败片段。参考 `recording.md`
使用明确的窗口 ID。页面真实可达时，涉及用户可见页面功能的最终录屏必须出现从页面入口到任务相关操作和结果的
真实路径；终端测试或页面 HTTP 200 不能替代页面功能证据。若应用因真实启动错误在页面可达前失败，则只录
Terminal 的实际失败过程，不启动 Chrome、不切换另一套环境补页面。Web 录屏的 Terminal 段结束后必须关闭所用
终端和临时会话，录制过程不得激活或置前任何录制窗口。

## 平台提交

- 当前 SOLO2 表单按服务端动态 schema 提交；轨迹和录屏分别上传，写入 `trace_file` 和 `screencast`。
- 提交平台地址、账号、密码存在性和认证会话只从本地工作台获取。技能禁止直接读系统 Keychain，
  禁止读取认证环境变量或复用缓存 Cookie；每次操作先校验平台返回账号与工作台配置完全一致。
- 自动提交开关 `submission.autoSubmit` 默认开启。`export` 完成后直接上传、提交并轮询；
  只有排障时才显式使用 `submit --dry-run`。
- `SUBMITTED` 只是已提交，不是通过。只有 `QC_PASSED` 是成功终态；`PENDING_FIX` 更新原记录的允许字段，
  `QC_REJECTED`、`QC_DISCARDED`、`QC_FAILED` 和轮询超时均需停止并保留平台原文。

## 质检重点

- 字段完整，SessionID / PromptID / 快照准确。
- 领域、子方向、任务类型、技术栈和难度分类准确。
- 题目真实、不雷同、不是过简题。
- 分数与描述一致，确实看过过程与产物，问题定位具体。
- Feedback 通顺自然，没有空泛评价、模板化和 AI 痕迹。
- 录屏与结论一致：画面失败时不能写成成功。
