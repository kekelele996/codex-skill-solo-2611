# 题面设计标准

本口径参考 `sologsb-0917/references/prompt-standard.md`，按 26.11 单轮 pointwise 执行形态调整。

## 设计顺序

1. 先读真实项目，至少找到 2–3 个已有业务文件和数据流。数据工程题优先看采集入口、解析/清洗逻辑、批次状态、持久化结构、回读接口和错误处理。
2. 写清当前业务在哪里卡住，以及实现错误后用户能看到什么。不要先写技术方案。
3. 只留一个真实冲突，但至少两条约束互相牵制。例如「迟到数据要保留」与「同一主键不能重复入库」，「失败要可续跑」与「重跑不能重复产生下游结果」。
4. 题面要能自然引出至少一项实质复杂度：并发、幂等、失败恢复、迁移兼容、权限边界、容量、离线合并、失效重算、跨系统对账、Schema 演进或迟到数据。
5. 写难度论证 `difficulty-review.json`，逐条回指题面原句与真实源码文件。门禁不通过不安装提示词。

## 自然表达

- 首轮优先 170 字以内，绝对上限 240 字。
- 像业务方当面交代需求。先说场景和问题，再说期望结果与不能接受的后果。
- 硬性措辞（只能、必须、不得、不能、一律、禁止等）最多 3 处；分号最多 2 个。
- 不使用 Markdown、文件路径、函数名、代码术语、端口、容器方案或具体技术栈。
- 不写「第几步改成什么」这类引导修复指令，也不写轮次。
- 不写「刷新后……一致」「并发后……只生效一次」这类历史模板收尾，改成本题特有的业务结果。
- 写完用固定版本 `ra-人话` 复读，填 `monitor/prompt/ra-renhua-review.json`，hash 必须对应最终题面。

## 机器门禁

`prompt` 会检查：

- 题面长度、Markdown、路径/代码词、引导修复措辞、轮次、端口、容器方案和具体技术栈。
- 硬性措辞与分号数量、历史模板尾句、ra-人话硬禁表达。
- 本机历史题精确重复、连续 12 字片段复用和相似度；`>=0.75` 阻断，`0.55–0.74` 警告。
- 难度结构、平台三项信号、跨对象不变量、真实源码文件、实质复杂度原句和中等形态自辩。
- ra-人话审核记录版本、题面 hash、硬禁项与未解决问题。
- 实际调用固定版本 `solo-annotation-loop/scripts/validate-prompt.py` 和
  `audit-human-writing.py`；校验器缺失时阻断。

`prompt --init` 会生成草稿和两份 JSON 模板。最终安装后题面写入 `delivery/提示词.md`；首轮执行后不得再改。
