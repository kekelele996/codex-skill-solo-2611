# Feedback 编写与复核指南

本期规范允许基于轨迹和产物形成结论，但要求 AI 给出的判断经过验证、文案自然且没有模板腔。Agent 可以读取原始轨迹、时间线、diff 和录屏后起草，标注专家必须逐条复核事实、分数和措辞。

Feedback 面向产品行为和交付结果，只写业务需求、实现后发生了什么、边界数据怎样处理。
正文不得出现“用户”。需要描述影响时，直接写业务对象、页面、任务、样本或可观察结果，
例如写“页面无法打开”“样本无法创建”，不要写“用户看不到页面”“用户无法创建样本”。
不得出现模型、助手、容器、Docker、临时依赖、本地脚本、录屏、终端、浏览器、提交、质检、返修、
SessionID、PromptID、轨迹等工作流信息。需要给证据时直接写业务动作和可观察结果，例如
“补齐列并重新解析后再次分析”，不交代由谁、在什么环境或用什么脚本完成。

## 三条总要求

1. **代码信息少写，能换成业务说法就换。** 文件名、函数名、字段名、枚举值、命令默认换成它对使用者的含义：
   `test_service_flow.py` 写成“服务流程的测试”，`checksum` 写成“上一批结果”，`inclusive/strict` 写成“边界是否包含当天”。
   必要时可以写，一般一两处就够，见下面的“什么时候可以写代码和数值”。
2. **具体数值少写。** 能用前后变化或定性结论说清的就不写数字：“取值保持不变”“少了记录”“处理进度停在原处”
   “列出了受影响的样本”。数字本身就是问题所在时，保留一个前后对照。
3. **语句通畅。** 按高中语文水平写：句子主谓宾完整，主语清楚，读一遍就能懂，不用回头重读。
   每句只讲一个因果，连接词放对位置，不堆名词串，不用口径、事后、对平这类行话，
   见下面的“用词：换成直白说法”。正文写“需求”“业务要求”，不写“题面”；没验证就说做完了，写“报告完成”。

其余细节（完整文件清单、命令输出、成组计数、ID）留在轨迹、产物快照和 `monitor/runtime-verification.json`，
审核时能回查即可。

## 先造证据，再写事实

`feedback --check` 分两层。文风层拦格式和禁词，事实层会把正文里的每个事实拿去和真实记录比对，
对不上直接阻断。事实层比对的是三份东西，全部由脚本自己生成，不接受手填：

1. **原始轨迹**：主会话和子代理里工具真实返回的输出、读过的文件路径、工具调用步数。
   模型自己说的话不算。
2. **产物快照**：初始快照到产物快照的文件清单、diff 统计和文件内容。
3. **本机真实运行**：`verify` 记录的退出码、stdout、stderr。

所以顺序是：读证据 → 跑 `verify` → 再写 Feedback。

```bash
python3 $S verify --task-root ROOT --label '重跑同一批看是否新增' -- python3 checks/verify.py
python3 $S verify --task-root ROOT --label '移走源文件后重试' -- python3 checks/fail_case.py
```

会被拦下的情况：

| 写法 | 为什么被拦 |
|---|---|
| 写“订单从 120 行变成 240 行”，但两次运行只输出过 120 | 数值不在轨迹、运行输出或需求原文里；差值必须能从两次真实输出算出来 |
| 引用 `src/dedupe.ts`，但产物和轨迹里都没有这个文件 | 文件路径不在快照和轨迹里 |
| 引用 `dedupeOrders()`，但产物里没有这个函数 | 反引号里的标识符在产物快照和轨迹里都找不到 |
| 写“报错 `column "t_id" does not exist`”，实际报错是 `tenant_id` | 反引号里的原文在运行输出和轨迹里都没有逐字出现 |
| 打 4 分，但 `verify` 没有一次成功退出 | 高分必须有一次真实跑通的记录 |
| 写“重试会失败”，但从没真跑过失败场景 | 写了失败表现，就必须有真实的失败输出 |
| 一句 `verify` 都没跑就写反馈 | 没有真实执行记录 |

不受影响的情况：需求原文里的要求、页面上的文案、`verify` 标签里的说明，都可以直接写。
正文里不留数字和代码时也不会有额外负担——这正是默认该有的写法。

判定依据写在 `monitor/feedback-evidence.json`，每条声明是“已核对”还是“查无来源”都能看到。
要把一条声明变成可核对的事实，就去补一次真实运行，不要改数字去凑。

### 什么时候可以写代码和数值

判断标准：删掉它，读者还能不能明白问题在哪、能不能定位。不能，就保留。

- 问题就出在某个具体位置，业务说法定位不了：改错了文件、漏改了某个配置项、迁移脚本没执行。
  例如“只改了接口层，`migrations/` 里的建表语句没有同步，新字段上线后写入即报错”。
- 页面或接口直接出现的报错或返回：报错原文、接口状态码，例如“导入时返回 500，提示 `column "tenant_id" does not exist`”。
- 需求本身点名的接口、命令或配置：需求要的就是 `/api/backfill` 或某个开关，照写更准确。
- 数字就是缺陷：行数翻倍、金额差一分、超时阈值写错、精度丢失。例如“重跑后订单从一份变成两份”能说清就不写数字；
  “金额多算了 0.01 元”这种差值本身就是结论，保留。

不必要的情况：只是为了显得有证据而列文件名，罗列测试名和通过数，抄内部字段名，把每一步的计数都写出来。

## 篇幅与信息密度

Feedback 是给人快速判断的短复盘，不是验收报告。

- 默认控制在 180–280 个非空字，超过 280 字警告，超过 360 字阻断。
- 只保留一两个最能支撑分数的判断，证据写成业务操作和可见结果，例如“改了特征定义再重跑，已有样本取值不变”。
- 需要证明“页面、接口和数据库一致”时，写一句核对结论即可，不把三边输出逐项粘贴。

## 测试证据与计数

- 测试证据必须直接对应题目的业务目标。写测试覆盖了哪些业务场景和不变量，一般不写测试文件名，
  不写“x/x 条测试通过”，也不拿与题目无关的前端类型检查充数。
- 产物段用功能机制描述实现，写清成功路径、失败路径和可观察结果。审核材料仍须能回查到对应改动和
  真实运行，不能把自然的功能描述当成未经验证的口头结论。
- 代码与运行证据确认功能已经可用时，使用确定表达，例如“能够”“可以”“能”“完成了”“已实现”。
  只写“统一切换”“清楚展示”会让读者无法判断这是能力、计划还是推测。
- 涉及读取、写入、忽略、拒绝时，优先写业务含义：哪些记录写进去了，哪些因为早已入库或版本更旧
  被忽略，几类数量能不能对上。数量对不上本身就是问题时，保留关键的前后值。

## 写前读什么

1. `traces/-workspace/<sessionId>.jsonl`：模型实际读过、改过、执行过什么。
2. `delivery/轨迹时间线.md`：脚本摘录的步骤索引，用来快速定位原始事件。
3. `workspace` 的产物 diff：最终交付是什么，不是模型口头说做了什么。
4. `recording/运行录屏.mp4` 和 `运行录屏-window-capture.json`：真实运行、失败过程和采集方式。
5. 题目要求、初始快照和产物快照：逐条判断需求是否实现。

## 交付完整性

只判断需求功能点是否完整实现、代码能否运行、有无虚假成功。1–5 分整数：

- 5：例外档。完整跑通全部明示需求，合理补全关键边界，没有虚假成功，也没有任何已知缺口；
  还必须通过 `references/score-calibration.md` 定义的严格满分审计。
- 4：常规高质量档。主要需求完成且可运行，但仍有一个或多个少量、具体、可说明的细节遗漏。
- 3：核心功能能跑，但存在明显 Bug 或轻微虚假成功。
- 2：主要需求未完成，逻辑/依赖导致不能运行，或较大比例虚假成功。
- 1：严重失败、答非所问，或报告完成后实际没改。

不能照抄评分表。默认把 `4` 作为高质量完成的上限，`5` 只用于证据链完整且没有残余缺口的例外情况。
`4` 分必须写明一个不能忽略但不足以降到 `3` 的缺口，例如尚未固化的自动化回归、只覆盖部分规模、
缺少分页或仍需人工补验。`5` 分必须填写并通过 `monitor/score-review.json` 严格审计：
逐项覆盖全部明示需求、至少两个关键边界、至少两条真实运行记录、回归与跨层回读，且 `knownGaps` 为空。
只有正常路径、单条成功命令、没有发现显式错误或仅靠自述，都不能评 `5`。

## Feedback 结构

反馈写成“过程问题”和“产物问题”两段，只保留决定分数的判断，每段两三句：

- **过程问题**写实现时的决定和验证行为：哪条规则设计错了、哪一步没实际跑过、凭什么报告完成、
  失败后怎么处理的。复核时怎么操作的不写。
- **产物问题**写页面、任务或报告里可见的结果：先用一句交代做成了的部分，再写失败项。每个失败项都说清
  页面上本该出现什么、实际出现什么、因此做不成什么。
- 同一件事只在一段出现：根因放过程段，业务上可见的后果放产物段。

正例（4 分，迟到补传合并）：

> 过程问题：第一次比较来源时间和目标表时间时发现解析有细微偏差，修正后，会员和门店单品两组迟到补传都得到了预期结果。测试覆盖了迟到行保留、旧版本忽略、重跑幂等，以及读取数等于写入、忽略和拒绝之和的对账，入库结果也与业务预期一致。
>
> 产物问题：逐项核对并运行后，门店补传批次只写入了符合最新版本的记录，其余因为早已入库或版本更旧被忽略，目标表保留了较新的商品记录，读取、写入和忽略数能够对上。问题是每次增量运行仍从头扫描整批源数据，没有只处理补传的对象，源数据越多耗时越长。

正例（5 分，功能描述型产物段）：

> 产物问题：成功批次完成时能统一切换可见版本，失败时只清理该批次产生的半成品；页面能清楚展示当前使用的批次、最近处理状态和列结构变化。移走源文件让批次失败后，原有的列结构没有被替换，恢复后再次重算可以成功切换；同一批次重试前后行数不变，没有新增记录。

这段写法的处理方式：

- 不写文件名或函数名，把实现转成成功切换、失败隔离和页面状态三条可见机制。
- 用“列结构没有被替换”“重试前后行数不变”证明旧结果保留和重试不新增，不需要写出具体列数和行数。
- “能统一切换”“能清楚展示”“可以成功切换”给出了明确完成判断，避免把已验证能力写成悬空的功能名词。

反例：

> 过程比较乱，模型没有认真检查。产物效果一般，存在一些问题，整体还需要优化。

## 通顺度：整段改写正反例

`feedback --check` 只能拦格式和禁词，拦不住“读起来生硬”。下面这段原稿门禁全过，读者读完仍说不清为什么是 2 分。

反例（特征平台点时间回填，2 分）：

> 过程问题：复核时创建任务固定 30 天、inclusive，改成 1 天、strict 后重跑 200 条样本，特征值逐项不变，口径冻结成立。第 2 步发送迟到新事件，水位向前推进并正确列出受影响样本。可更正原事件后，金额已替换，任务却报错并把水位停在 1200，连续重跑无法推进；撤销也未实现。重复投递被忽略后，报告显示重复数 0，影响清单为空。
>
> 产物问题：回填页能展示台账水位和未对平诊断，也会保留旧 checksum，但同一屏仍显示“对平 / 成立”，影响区域沿用上次成功批次的新增记录，没有列出本次替换影响的样本；页面上也没有处理更正或撤销的入口。

问题在哪：

- 过程段写成了复核步骤（“复核时”“第 2 步发送”），没写实现时做了什么。真正决定分数的两件事一句没提：
  改动已入库事件的投递一律被判成结果对不上；入库这一步没实际跑过就报告完成。
- 数值和英文参数原样堆砌：“30 天、inclusive，改成 1 天、strict”“200 条”“1200”，读者要自己翻译成“改了特征定义”。
- 内部字段名进了正文：“checksum”。
- 错字和转折错位：“可更正原事件后”应为“但更正……后”。
- 只列现象，不说该是什么：“重复数 0，影响清单为空”没说明读者本应看到被忽略的那条投递。
- 事实不准：撤销其实写进了台账，只是任务同样失败，写成“撤销也未实现”是误判。
- 成立项和失败项混排，两段又各说一遍更正失败和影响清单，主次不清。
- 名词串读不通：“影响区域沿用上次成功批次的新增记录”。
- 行话多：“口径冻结”“对平 / 成立”，读者得先猜这些词指什么。

正例（同一题，事实已回查轨迹和真实运行；这题的问题都能用业务说法讲清，所以没有保留代码和数值）：

> 过程问题：设计回填规则时，只要新数据改动了已经入库的事件，就判定结果对不上，所以需求里的更正和撤销都会让任务失败。更正一笔金额后，处理进度停在原处，重跑多少次都无法推进。入库这一步从没实际运行过，服务流程的测试写好后又被删掉，只验证了计算部分就报告完成。
>
> 产物问题：已有样本可以按创建时的特征定义重新计算，之后修改定义再重跑，结果也不会变；迟到的新事件能够补进来，受影响的样本也会列出来。重复的数据在入库时被直接跳过，报告里却没有任何提示，有记录被忽略也查不到。回填页面上同时显示上一批结果一致、本批结果对不上，影响列表也没有更新，无法判断现在的结果能不能用。

改法：

- 过程段只写实现时的决定和验证行为，复核操作一律不写。
- 产物段先一句交代做成了的部分（说明为什么不是 1 分），再写失败项，每项带上“页面或接口本该呈现什么”。
- 参数和数值翻译成业务说法：“30 天改 1 天、inclusive 改 strict”写成“改了特征定义”，“特征值逐项不变”写成“已有样本的取值不变”。
- 行话换成直白说法：“口径冻结成立”写成“能按创建时的特征定义重算”，“对平 / 未对平”写成“结果一致 / 结果对不上”。
- 每句只讲一个因果：“规则设计错 → 更正必然失败”一句，“更正后进度不动、重跑无效”一句，“没跑过就报告完成”一句。

## 通顺度：句子级正反例

| 反例 | 正例 | 要点 |
|---|---|---|
| 复核时把窗口改成 1 天后重跑 200 条样本，特征值逐项不变 | 之后再改特征定义并重跑，已有样本的取值不变 | 不写复核动作，不写数值，直接写业务操作和结果 |
| 写好的 `test_service_flow.py` 又被删掉 | 服务流程的测试写好后又被删掉 | 文件名对定位没帮助时，换成它测的是什么 |
| 新字段上线后写入报错 | 只改了接口层，`migrations/` 里的建表语句没有同步，新字段上线后写入即报错 | 问题就出在具体位置时，保留路径反而更清楚 |
| 也会保留旧 checksum | 结果对不上时能保留上一批结果 | 字段名换成它的业务含义 |
| 任务报错并把水位停在 1200 | 任务报错，处理进度停在原处 | 数值换成前后变化 |
| 可更正原事件后，金额已替换，任务却报错 | 但更正原事件后，金额已经替换，任务却报错 | 写完通读一遍，查错字和转折词 |
| 报告显示重复数 0，影响清单为空 | 报告里看不出有记录被忽略 | 现象后面接上“读者本该看到什么” |
| 撤销也未实现 | 撤销能写进台账，但同样让任务失败 | 区分“没做”和“做了但结果错”，写哪种都要回查 |
| 影响区域沿用上次成功批次的新增记录 | 影响列表还停留在上一批 | 拆掉名词串，用读者能直接懂的说法 |
| 口径冻结成立 | 样本任务能按创建时的特征定义重算 | 用确定表达写能力，不用“成立”“生效”这类判词收尾 |
| 同一屏仍显示“对平” | 回填页面上同时显示上一批结果一致、本批结果对不上 | 行话换成读者一看就懂的说法 |
| 样本任务能按创建时的特征定义重算，之后再改定义并重跑，已有样本的取值不变 | 已有样本可以按创建时的特征定义重新计算，之后修改定义再重跑，结果也不会变 | 少用缩略词（重算、取值），写完整的词 |
| 重复投递在入库时被直接跳过，报告里看不出有记录被忽略 | 重复的数据在入库时被直接跳过，报告里却没有任何提示，有记录被忽略也查不到 | 转折用“却”点明，后果落到业务结果上 |
| 题面要求合并的更正和撤销都会让任务失败 | 需求里的更正和撤销都会让任务失败 | 不写“题面”，写“需求” |
| 只验证了纯计算部分就宣称完成 | 只验证了计算部分就报告完成 | “宣称”带情绪，写“报告完成” |
| 门店补传批次共 203 条，写入 2 条，其余 201 条被忽略 | 门店补传批次只写入了符合最新版本的记录，其余因为早已入库或版本更旧被忽略 | 计数换成每类记录的业务含义 |

## 用词：换成直白说法

读者是看不到实现细节的复核人，行话和生造词要先翻译才看得懂。下面这些词默认不用，`feedback --check` 会给出警告：

| 别写 | 改成 |
|---|---|
| 题面 | 需求、业务要求 |
| 宣称完成 | 报告完成 |
| 口径、口径冻结 | 计算方式、特征定义、统计规则；“能按创建时的特征定义重算” |
| 事后 | 之后、后来；“之后再改定义并重跑” |
| 对平、未对平 | 结果一致、结果对不上、数量能对上 |
| 落地 | 实现、做到 |
| 闭环、抓手 | 写清具体做了什么 |
| 兜底 | 失败时怎么处理 |
| 链路 | 流程、这一步；“入库这一步没实际跑过” |

“成立”“生效”“水位”这类词不报警，但也尽量换掉：“成立”换成“能”“可以”，“生效批次”换成“当前使用的批次”，
“水位”在读者不熟悉时写成“处理进度”。需求本身用了某个词、页面上就显示这个词时，可以照写，最好加引号。

## 通顺度自检

写完按顺序过一遍：

1. 出声读一遍。读着要换气、要回头重读的句子，按“触发—行为—后果”拆开。
2. 搜一遍数字和英文：文件名、函数名、字段名、枚举值、具体数值，能换成业务说法的换掉；
   删掉后读者就定位不了问题的，留下，一般不超过一两处。
3. 搜一遍行话：题面、宣称、口径、事后、对平、落地、链路这类词换成直白说法。
4. 每句主语是否清楚：是实现时做的决定，还是产品运行时的表现。不写“模型”，但也不能让读者猜。
5. 每个失败项是否写了期望：需求要什么、页面或接口本该呈现什么。
6. 两段之间有没有重复：根因放过程段，业务可见后果放产物段。
7. 只看这两段，能不能明白为什么给这个分数。

## 只写模型能力问题

网络波动、网关 429、镜像拉取失败、宿主机权限或误操作不进入 Feedback。结构问题导致没有有效一轮时按规范重新 roll，不提交无反馈价值的数据。

## 数据工程常见证据

复核时逐项核对下面这些，写进 Feedback 时优先转成定性结论（“能够对上”“没有重复写入”“少了记录”），
数字本身就是缺陷时再保留：

- 源记录数、解析成功数、隔离数、入库数和回读数是否等于预期。
- 同一 fixture/批次重复执行后的行数、版本和下游结果是否幂等。
- 迟到事件、旧事件、乱序事件到达后，是否被正确拒绝、覆盖或保留版本。
- 中断后续跑是否从正确水位开始，是否重复写入。
- Schema 新增/删除字段后，旧数据能否读取，新坏行是否被隔离。
- 源库与数仓对账差异能否分类、定位和只修复异常分区。
- 构建、启动、任务退出码、错误日志、接口状态和最终业务结果。

## 去 AI 味自检

- 事实要直写：写“回读比源数据少了记录”，不写“从录屏来看好像少了一行”。
- 少用空转词：真正、其实、本质上、核心在于、更重要的是、综上。
- 不用“不是 A 而是 B”“不仅 A 还 B”这类模板句。
- 同一件事只说一次，不把过程问题和产物问题互相复述。
- 句子按因果自然连起来，不堆名词串和一句一条的清单。
- 不引用本地临时脚本、验收脚本或 Playwright 场景来证明模型产物质量。
- 不写任何运行载体和交付流程，验证事实直接落到业务动作、数据变化、接口返回或页面结果。
- 结束前把每个结论、报错和需求点回查一次轨迹或本机真实运行。
