  题面送入 tmux 后，监督器进入该函数会触发 `RecursionError`，随后被外层记成会话丢失，

  内容完全一致的第一条真人消息，才写 `prompt.sent` 并进入第 1 轮。

  同文重发。75 秒仍无匹配轨迹才按 `start_failed` 收尾，不消耗会话机会，由调度器重新排队。
- 所有补发只作用于当前 tmux/Claude Code 会话，不重新创建提示词，也不会把同一道题另开一条会话。

## 2026-11-13 P4 同案材料归并被误判为困难

- 一道“同一案件、同一材料类型按内容归并，保留主件并显示重复来源”的题通过了旧的三个信号门禁，
  但 SOLO2 按 P4 判为中等并废弃。旧门禁把页面展示和文件数量当成多模块整合，把输入重复后的去重
  当成幂等，也过度信任手填的 `passed=true`。
- 该题的核心仍是单点判重规则：页面只是展示主件、重复来源和判定依据，结果表没有独立责任。
  题面中的“重复投递后不新增”描述的是数据质量去重，不属于重跑、重新运行、重试或断点续跑后的幂等。
- 技能升级到 0.5.0：难度模板改为 `schemaVersion: 2`，新增 `platform-p4-v2` 合同，强制至少三个运行边界、
  两个不同 kind 的独立责任边界、两个真实源码文件、状态迁移、跨边界契约和两类原句风险。
- 页面、结果表、弹窗、同一算法拆出的函数不再算独立责任边界。代码量、文件数、测试数和页面区域数
  不能把中等题升级为困难题。过去填满三个模块或 `passed=true` 也无法通过。
- 出题前必须问：“如果页面完全不存在，剩下的是否仍是需要跨边界协调的困难问题？”答案为否时换题。
- 无法填写至少三个运行边界、两个独立责任边界和两类原句风险，在进入 `repo` 和 `run` 前阻断。
  正确做法是换成真正有采集、持久化、恢复、发布、对账等运行边界的状态型任务，不是修改措辞。

## 2026-11-13 V2 按轨迹复核 Feedback 能力层级

- 一次质检已通过的数据在复检时被 V2 打回：轨迹明确记录没有 pip/Docker、后端只能做语法级检查，
  但 Feedback 写了“验证了规则调严、删除、同名重报和重新执行”，平台判定为反馈与轨迹不符。
- 这类错误不是措辞问题，而是把“代码已实现/静态检查通过”外推成“业务链路已运行”。
  主会话轨迹会限制 Feedback 能声称的最高验证层级，本机另行补跑也不能改写平台对轨迹的判断。
- `feedback --check` 新增轨迹能力对齐审计：识别轨迹中的运行受限声明，并拦截 Feedback 里越过该上限的
  “验证了/跑通/真实回读/业务链路验证”等表述；结果写入 `monitor/feedback-trace-audit.json`。
- 正确写法是分别陈述“代码已让…”和“数据库迁移/同名重报/报告导出没有运行验证，仍是缺口”，
  让实现事实、验证层级和扣分点保持同一口径。

## 2026-11-12 4 分 Feedback 要显式写出扣分点

- 实测中，4 分反馈虽然通过了 `feedback --check`，产物段也写了“台账只展示最近一段记录，
  没有翻页或继续加载”，但复核人仍反馈“没有明显看到扣分项”。门禁能定位缺口，不等于读者一眼能看见。
- 4 分产物段先写已经确认完成的能力，再单独用“扣分点是……”起句。该句要同时写清具体页面或功能、
  实际表现和业务影响，不能把缺口藏在能力描述后面。
- 本题可作示例：

  > 跨流队列页面能显示两条流的处理进度、暂存与放行数量、缺失客户、阻断记录和状态变化；
  > 故障恢复后回读，订单没有重复发布。扣分点是订单台账只展示最近一段记录，没有翻页或继续加载；
  > 历史积累后，较早的暂存与阻断记录会从页面消失。

- 门禁层仍要求缺口所在分句可定位；人工复核再要求扣分项醒目、具体，避免“事实存在但读者看不出来”。

## 2026-11-12 Feedback 事实核对与真实结束判定

- `feedback --check` 原来只有正则：它能拦禁词和格式，拦不住编造的数字、文件和报错。
  新增 `scripts/evidence.py`，由脚本自己从主会话与子代理轨迹、产物快照、`runtime-verification.json`
  建索引，把正文里的数值、文件路径、反引号标识符和报错原文逐条回查，查不到即阻断。
- 索引只收工具真实返回的输出。模型在轨迹里说的话、`verify` 的命令参数都不作为事实来源——
  否则先把编造的数字写进命令参数再执行一次就能绕过。`echo`、`python3 -c`、`bash -c` 直接拒绝。
- 两次运行输出之间的差值、倍数算可核验数字，避免“必须凑到原文”逼着人去改数字。
- 至少一条真实执行记录是硬门槛；4–5 分要求有一次成功退出；写了报错/失败表现就必须有真实失败输出。
  实际测下来，编造的“240 行”被精准拦下，改为真实输出里的“120 行”后才通过。
- `run`/`collect` 增加 `trace.completion_review`：`end_turn` 只说明进程退了。最终回复在向用户提问、
  还在许诺“接下来我会…”、有 tool_use 没有对应 tool_result、出现上下文耗尽/超时痕迹、回复断在句子中间，
  都按未完成处理并重新 roll，判定写进 `attempts[].completion`。
- 端到端测试里故意保留了两次 `SystemExit`：没有执行记录时拒绝、反馈数字与真实输出不符时拒绝。
- 补 `tests/test_evidence.py` 后立刻抓出三个问题，都是端到端测不出来的：
  1. 路径检查从被掩码过的文本里找，`PATH_CLAIM` 已被抹掉，这一层实际上从没生效过。
     现在数字用掩码文本（避免文件名里的版本号被当成声明），路径用原文。
  2. `CLAIM_NUMBER` 原来用 `\w` 做边界，Python 的 `\w` 含汉字，`订单120行` 这种最常见的
     中文写法整体漏掉。改成只排除 ASCII 标识符字符，中英混排都能抽出来。
  3. 轨迹里模型自己敲的命令文本也算数值来源，等于把数字写进命令参数再执行一次就自证了。
     现在命令文本只给函数名和报错原文作证，不给数字作证——和 `verify` 参数同一条口径。

## 2026-11-10 数据工程改版

- 本期默认方向改为「数据工程 / 其他」，区分的是多渠道、上下游延伸或边界混合的数据工程任务，不是通用后台。
- 2026-11-11 分类更新：安全增加身份认证、网络与通信安全、系统安全；图形增加游戏开发、图像处理；数据工程增加数仓与数据湖、数据分析与数据应用，并取消游戏和数据工程下的「其他」兜底。
- 大类下所有合法子方向都允许出题，例如数据工程三个子方向均可直接用于 `init` 和 `prompt`。旧配置中的合法领域/子方向不再被迁移覆盖。
- `prompt` 现在必须先铺并填写难度论证与 ra-人话审核记录。题面原句引不到、源码文件不存在、复杂度只靠文字自证都会被阻断。
- Feedback 不再套用“禁止分析轨迹”的旧限制；结论必须回到原始 JSONL、diff 和真实运行反复核对，再由专家复核。
- 录屏改为显式窗口 ID。Chrome 必须由 `record chrome-start` 用临时 profile 新开，`record start` 会拒绝用户已有 Chrome。
- 录屏固定不采集指针，并生成 `运行录屏-window-capture.json` 与 `运行录屏-cursor-guard.json`；`status` 会检查这两份证据。
- 同一 Python 进程内连续 `record start/stop` 时，录制器退出后会短暂留下僵尸进程；`_alive()` 必须先用
  `waitpid(WNOHANG)` 回收，再判断 `kill(0)`，否则会误等 45 秒后报“没有落盘”。

## 2026-11-11 页面录屏补充

- 一题虽然主要验证后端状态指纹和幂等，但只要交付同时修改了影响分析页面，terminal-only 录屏就不完整。
- 录屏模式按用户可见功能判断；Web 计划的 `pageSteps` 为空会被门禁阻断。
- 页面段必须展示任务相关操作和结果，登录页、首页或 HTTP 200 截图都不能代替功能验收。
- 服务应先清空数据，再在 Terminal 镜头里真实启动；构建和服务若在开录前就已经启动，不能只补录健康检查冒充启动过程。
- Chrome 的密码保存、同步或通知浮层会遮挡结果，独立临时 profile 需要预先关闭密码管理并过滤这些浮层。
- 录完 Terminal 段立即执行 `record terminal-stop`，不要让它留在桌面等待 Chrome 段。
- 不允许用 `activate`、`open -a`、AX 提窗或前台切换驱动录制窗口；这会抢用户的鼠标和焦点。

- GitHub 仓库名改用独立的 `repo_slug`：先替换常见业务术语，剩余中文用系统转写生成拼音，
  无法转写时再落到稳定哈希；最终名称始终含 ASCII 项目词和 4 位随机后缀。
- 该修复只约束后续新建仓库；历史仓库保持原名，不执行批量改名。

## 2026-11-12 实测修正

- 中文任务名不能直接拼入 Docker `--name`：即使普通路径允许中文，Docker 仍只接受
  `[a-zA-Z0-9][a-zA-Z0-9_.-]`。本题首次启动因此在建容器前失败，后续必须使用独立的
  `container_slug()`；普通任务目录和仓库名仍保留更友好的 `safe_slug()`。
- `record terminal-stop` 发出关闭后，ScreenCaptureKit 的窗口枚举可能仍短暂看到旧窗口。
  清理证据应在 5 秒内轮询确认窗口消失，不能立即判失败；实际关闭后再次运行命令也可修正报告。
- ScreenCaptureKit 的 `--list-windows` 偶尔会卡到 30 秒超时，不能让它成为 Terminal 清理的唯一
  依赖。窗口是否关闭改用 Terminal 自身的 AppleScript 窗口计数；计数失败时保守记为未确认，
  不能为了通过门禁伪造已清理。
- 页面包含 1200 行台账表时，`wait_for_function(document.body.innerText.includes(...))`
  每帧读取整页文本会拖死渲染。改为轮询任务状态，结束后 reload 一次，再用 heading/业务元素定位。
- 导航链接和页面标题常出现完全相同的文案；页面自动化先无录屏完整走一遍，并用
  `get_by_role("heading", ...)` 等语义选择器消除 strict mode 歧义，再进入正式录制。
- 页面题如果真实启动在登录页或业务页之前失败，页面本身就无法验收。此时 Terminal 失败录屏是完整证据，
  不能另起一套成功环境或把另一条路径的页面拼进来硬凑 Web 录屏。
- Codex 桌面端最终汇报不能只给录屏链接和 Feedback 摘要：视频要用 Markdown 媒体嵌入直接播放，Feedback
  正文要原样展示，其他交付文件用绝对路径集中列出。
- 启动确认页偶发卡住的原因是 `Down` 和回车只隔 0.2 秒：负载高时两个键被 Claude Code 合并处理，
  回车落在默认的 `No, exit` 上，容器直接退出，而旧逻辑还会对着已经消失的会话干等 60 秒。
  处理确认页必须“移动光标 → 回读屏幕确认高亮在 Yes → 再回车”，并在 tmux 会话消失时立即返回。
- 可见终端窗口用 `exec tmux attach` 打开后，Terminal 的 `busy` 属性始终为 false，不能用它判断
  会话是否还在；窗口能否关闭只看 tmux 会话是否存在。自定义标题也不一定生效，认领窗口要同时
  匹配标题和启动命令。
- 可见终端窗口不能 `activate`：抢到键盘焦点后，用户正在别处输入的按键会落进受管会话，
  也是确认页被误选的来源之一。窗口默认只读接入。
- 单元测试里凡是会走到 osascript 的路径都要替换 `terminal_view._osascript`，否则测试会在本机
  真的弹出 Terminal 窗口。
- 容器超额的原因是容量检查只做在打印模式里：默认的受管模式和 supervisor 重启完全不查上限，
  多个会话各自执行 `run` 就会超过 `maxContainers`。容量检查必须放在所有启动路径共用的一处，
  并且把“已放行但容器还没出现”的启动也算进占用，否则同时启动的几个会话看到的都是旧数字。
- `common` 在导入时就确定配置路径和状态目录。测试文件各自在导入前设置环境变量的做法依赖收集
  顺序，新加一个排在前面的测试文件就会让整套测试读写真实的 `~/.codex/solo-2611`。隔离必须写在
  `tests/conftest.py`，并用会话级检查确认状态目录在临时目录内。
- 质检打回后不能直接按质检意见改写评分和 Feedback。返修内容要重新通过轨迹证据核对；与已提交
  版本出入较大（评分差 2 分及以上或正文大幅改写）时停在 `local_review_required`，由专家对照
  轨迹核验后再提交。

## 2026-11-14 长时间运行与窗口回收

- 确认页有时只用反色块表示选中，终端抓屏里看不到 `❯`。旧兜底在连续几次识别不到高亮后会先按 Down
  再回车，若默认本来就在第一项 Yes，反而会选中第二项 No。现在无标记时：Yes 在第一项先 Up 归位，
  Yes 在第二项才 Down；编号、箭头、中文“是/否”都能识别。
- `exec tmux attach` 退出后 Terminal 是否自动关窗取决于用户的 profile 设置，不能假设系统会替技能清理。
  可见窗口改为启动 `terminal_view.py attach-session`，attach 返回后按自己的 tty 主动关闭；即使监督器
  被 SIGKILL，这个适配器仍能执行 finally。工作台每分钟再调用一次 `terminal-sweep` 兜底旧版本残留。
- 单会话 3 小时是硬下限。工作台旧的 `stale_after_seconds=5400` 与技能的 10800 秒不一致，已同步为
  至少等于会话上限，避免 90 分钟后把仍在正常工作的会话误判为陈旧。
- 工作台调用 `run` 原来只等 15 秒，首次拉镜像或 Terminal 响应慢时会把仍然成功的启动误判为失败。
  现在启动调用有 300 秒窗口，失败后先用 `run-status` 检查容器/tmux/监督器，能接管就 `resume`，
  不能接管才进入启动失败退避。
- 容量锁不能只看标签：旧版本或人工操作可能留下没有标签、但名称仍是 `solo2611-*` 的容器。
  Docker 实况和降级探测都同时识别标签与名称前缀。启动过程抛错时，只有 Docker 确认容器未运行才归还
  租约，防止状态落盘失败后同一名额被再次放行；租约崩溃宽限从 5 分钟提高到 15 分钟。
- 8099 工作台的失败题清理原先只处理 `quarantined`。现在 `failed` 队列项同样走自动清理，清理完成后
  不等待下一轮定时器，直接触发补位；导出过或已提交 SOLO2 的题仍保留现场，不误删交付证据。
- Feedback 事实层能查数字和文件，但“轨迹明确说未完成、正文整体说已完成”仍可能逃过逐项锚点。
  新增总体意见一致性审计：冲突时写 `feedback-consistency-review.json`，退出码 4，专家批准后才继续；
  正文或评分改变后指纹变化，必须重新核验。
