# 困难 / 地狱题判定

本口径按 `sologsb-0917` 的 G16/G17 修订收窄，并针对数据工程补充幂等、迟到数据与 Schema 演进信号。

## 平台三项特征

1. 多模块整合：跨已有模块、数据所有权或上下游边界，并带出必须同时守住的不变量。
2. 关键设计取舍：互相冲突的业务约束要求选择事实来源、事务/分区边界、版本策略、补偿或回滚方式。
3. 复杂技术关注点：并发、幂等、失败恢复、迁移兼容、权限/租户、容量、离线合并、失效重算、对账、迟到数据或 Schema 演进。

`困难` 至少满足两项，并且关键设计取舍或复杂技术关注点至少有一个成立。`地狱` 三项都成立，还要另有开放方案判断、隐蔽约束、架构级取舍、多步深水调试或跨系统恢复。

## 数据工程直接判中等的形态

- 给现有采集脚本加一个字段、一个筛选、一个状态文案或一张结果表。
- 普通 CSV 导入、单表清洗、静态页面抓取或把脚本包一层命令行。
- 只把多个来源按顺序读进来，没有冲突裁决、恢复、幂等或对账要求。
- 只靠文件多、表多、步骤多或测试多制造难度。
- 普通管理页面加批量导入、报表导出或任务列表。

## 强制证据

每条困难/地狱题都必须填写：

- `signals`：三项特征分别可否成立，附真实源码证据。
- `platformSignals`：每项都有回答、题面原句和缺失后的可见后果。
- `crossObjectInvariant`：至少两个对象名真实出现在题面里，并写清不变量和背离后果。
- `projectEvidence`：困难题至少 2 个、地狱题至少 3 个真实存在的源码文件，并说明现有数据流。
- `substantiveComplexity`：题面原句必须体现声明的复杂类型；地狱至少两类。
- `hellSignal`：只有地狱题需要。
- `mediumShapeDefense`：题目形似“在现有模块补一层”时必须解释真正复杂度。

自由文字自证不算证据。题面引不到、源码文件不存在、对象名没出现，`prompt` 直接阻断。
