# 交付完整性满分校准

## 目标

交付完整性用于区分任务完成质量，不是“没有看到显式错误”就自动给满分。常规高质量交付默认评为 `4`；`5` 只保留给完成度、边界覆盖和证据链都达到苛刻标准的情况。

这个口径直接来自评分定义：`4` 对应“主要需求完成且可运行，只有少量细节遗漏”，`5` 对应“完整跑通全部明示需求，合理补全边界，没有虚假成功”。因此，只要还有已知缺口、未固化的关键验证或无法解释的风险，就应停在 `4`。

## 为什么满分要更严格

- 一次成功运行只能证明某条路径可以工作，不能证明失败路径、重复执行和跨层结果同样正确。
- 模型自述、编译通过、单个正常样例和页面可打开，都不能单独证明复杂任务已经完整。
- 复杂任务的边界条件通常互相牵制。只有同时验证成功、异常、恢复和对账，才能支持“没有已知缺口”的判断。
- `5` 代表接近理想交付，不是熟练完成的默认奖励。证据存在任何无法闭合的环节时，应使用 `4` 或更低分数。

## 评分决策

### 常规上限：4

满足以下情况通常评 `4`：

- 主要需求已经完成并能真实运行。
- 至少一条与需求直接相关的成功路径有执行证据。
- Feedback 能指出尚存的小缺口、覆盖限制或后续维护风险，并写明具体页面、功能点或验证环节。
- 没有阻断性错误或虚假成功。

只写“完整流程缺少回归”或“整体还需要人工复验”无法定位缺口，应按未通过处理；
必须说明哪条业务路径没有覆盖，例如“错误查询保护和修正发布只有一次性验收，项目内没有对应自动化回归”。

### 5 的必要条件

只有同时满足全部条件才能考虑 `5`：

1. 逐项核对所有明示需求，每项都有真实行为证据。
2. 至少两个关键边界或异常场景得到验证，不只覆盖正常路径。
3. 至少两条独立运行记录能支持结论，且成功路径有一次真实成功退出。
4. 关键结果已在处理层、持久化层和用户可见层之间回读一致，或按题目实际涉及的数据边界等价验证。
5. 重跑、恢复或相邻回归场景已验证，没有新引入的可见问题。
6. 不存在已知缺口、临时绕过、未覆盖要求或需要后续人工补做的核心工作。
7. Feedback 没有负面缺陷描述，也没有用模糊措辞掩盖残余风险。

以上条件必须写入 `monitor/score-review.json`。缺少文件、任一检查项为假、存在已知缺口，或运行证据不足时，`feedback --check` 会阻断 `5`。

## 降分规则

- 只有正常路径，没有异常或恢复验证：最高 `4`。
- 只有编译、静态检查或单元测试，没有业务结果回读：最高 `3`。
- 存在分页缺失、非核心回归未固化、只支持部分规模或仍需人工补验：通常为 `4`。
- 核心需求未完成、主要路径不可运行或报告完成但实际未改：按评分定义继续降分。

## 使用方式

`feedback --init` 会生成 `monitor/score-review.json` 模板。考虑评 `5` 时逐项填写；默认评 `4` 时无需伪造满分材料。

审计中的运行证据至少包含两条不同记录，`covers` 只使用以下标签：

- `success`：正常主路径。
- `negative`：失败、拒绝或异常隔离路径。
- `regression`：重复执行、恢复、旧行为或相邻能力回归。
- `cross-layer`：处理结果与持久化、接口或页面回读一致。

结构示例：

```json
{
  "explicitRequirements": [
    {"requirement": "需求原文", "verified": true, "evidence": "真实执行后的结果说明"}
  ],
  "edgeCases": [
    {"case": "重复执行", "verified": true, "evidence": "重跑后的客观结果"}
  ],
  "runtimeEvidence": [
    {"runIndex": 1, "covers": ["success", "regression"], "observation": "成功与重跑结果"},
    {"runIndex": 2, "covers": ["negative", "cross-layer"], "observation": "异常与回读结果"}
  ]
}
```
