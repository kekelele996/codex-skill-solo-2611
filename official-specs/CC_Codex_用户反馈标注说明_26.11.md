# CC/Codex 用户反馈标注说明（26.11领域专项）

## 一、项目背景

> 💡 我们希望还原用户在真实使用 Coding Agent 产品过程中的反馈信号，以判断模型是否真正满足了用户需求，并基于这些数据进行后续模型训练与持续优化。为此，我们计划标注一批真实用户在使用 Coding Agent 过程中的环境、轨迹与高质量用户反馈数据，共建 Coding Agent 能力。

1. **第一步，围绕上述重点领域出题并记录初始快照。**&#x786E;认题目属于上述重点领域与子方向，且难度为「困难」或「地狱」。出好题后在已配置就绪的工作区提交一次并 push 到远端，拿到 40 位完整 SHA 的 commit permalink，作为「初始环境快照」。

#### 📹 快照与仓库要求

- **快照格式：**&#x521D;始环境快照填 commit permalink，格式为 `https://github.com/<org>/<repo>/commit/<40 位完整 SHA>`。使用完整 SHA，不要填短 SHA、分支名或 tag：分支和 tag 会随后续提交移动，事后无法还原当时的状态。仓库需要 push 到评测团队可访问的远端，push 到个人私有仓库等同于没有记录。已提交的快照不要再做 force-push 或 rebase，历史改写会让记录的 SHA 变成不可达对象。
- **凭据不要进仓库：**&#x63D0;交工作区前确认 `.gitignore` 已覆盖 `.env` 以及各类密钥、连接串和 token 文件。需要说明外部依赖时，只写类型与版本，不要写真实连接串、账号或 token。
- **整个会话只提交一次快照：**&#x5728;首轮开始前提交一次即可，这意味着模型产出的代码变化完全由轨迹里的工具调用记录承载，因此 SessionID 与 TurnID/PromptID 必须准确回填：这两个字段一旦填错或漏填，这一轮的产物就再也无从追溯，会因为无法质检而打回。根据团队内部管理需要，也可以让大家每一轮都提交一下产物，目前不强制，可以写一个自动提交的 hook 来提效。

1. **第二步，使用 `auto` 模型执行单轮任务并留存产物。**&#x5168;程使用 `auto` 模型跑，只跑首轮（每一个 session 仅可进行一轮有效交互），模型给出回答后本轮即结束，不要追问、不要纠错。跑完后依次留存：
   - **产物快照：**&#x63D0;交工作区产物并 push 到远端，拿到 40 位完整 SHA 的 commit permalink（若模型自己提交了多次则填最后一个，不要 squash；「初始环境快照」必须是它的祖先提交）；
   - **运行录屏：**&#x5F55;制一段产物实际运行的视频并上传至对象存储；
   - **轨迹与会话 ID：**&#x8BB0;下本次会话的 `SessionID` 与 `TurnID/PromptID`，导出 `~/.codex/sessions/` 或 `~/.claude/projects/` 下对应的轨迹 `.jsonl` 文件并上传至对象存储。

#### 📹 录屏要求

录屏的目的是证明产物真实性，以及专家确实对产物有所衡量。所以录的是产物的实际运行，要求如下：从干净状态启动，完整展示真实输出；无法运行的也必须录，把报错过程录出来；不要剪掉失败或不好看的片段；时长控制在 90 秒以内（720p、mp4），对于文件较大的情况（>10MB），传到对象存储后在表中填可直接播放或下载的链接。

> ⚠️ 任务难度的分级如下表。需要专家根据 repo、技术栈、题目从人类执行的视角判断任务难度。

| 任务难度 | 描述                                                                                                                                                 |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 简单   | 任务意图明确，主要沿已有模式做机械修改或局部实现；即使改多个文件，只要模式高度一致、核心判断很少，也算简单。<br /><br />**请注意：首轮任务中，严禁出简单题和中等题。**&#x4F46;是后续轮次中，可能因为模型产物质量不佳而产生较为简单的 bugfix，这部分数据是允许提交的。 |
| 中等   | 需要理解局部到跨模块的调用/数据流，做一些实现决策；有若干边界条件或约束，但不需要重新设计架构。                                                                                                   |
| 困难   | 需要整合多个模块/系统约束，做关键设计取舍，处理复杂状态、兼容性、权限、并发、性能或异常链路。                                                                                                    |
| 地狱   | 人执行起来需要极高的决策复杂度，通常需求很开放或约束很隐蔽，需要极其深度项目理解、架构级判断、多步复杂的调试验证，或正确性依赖大量边界场景。即使当前的 SOTA 模型也无法成功交付。                                                        |

| 维度              | 描述                                            | 5 分（完美/超预期）                                  | 4 分（优秀/小瑕疵）                           | 3 分（及格/勉强可用）                                       | 2 分（不及格/需重构）                                                | 1 分（完全不可用/严重事故）                                     |
| --------------- | --------------------------------------------- | -------------------------------------------- | ------------------------------------- | -------------------------------------------------- | ----------------------------------------------------------- | --------------------------------------------------- |

## 3. 不应该考虑的因素

- **推理的时长：**&#x53EF;能受模型部署影响。不要把推理时长考虑进去，对于效率的衡量可以看轮次和篇幅。
- **模型戛然而止（无报错）：**&#x53EF;能受到部署和 harness 适配的影响。遇到了尽量重新 roll，如果实在 roll 不出来一直无故中断（非 api 报错）就换题目。
- **网络工程错误（有报错）：**&#x4E0D;考虑网络波动、请求失败这类工程故障，遇到就重新 roll，持续报错就联系我。

## 三、质检点

1. **整体质量维度**
   - 数据总量统计
   - 整体合格率
   - 数据多样性（是否覆盖了各场景，是否出现了雷同的题目）
2. **标注合规性**
   - 轮次合规（是否超 10 轮、窗口拆分是否正确）
   - 字段完整（是否有字段缺失）
   - 题目分类准确性（任务类型、技术栈、难度）
   - 打分与描述一致性（是否在原因中提到产物有问题却标注了任务完成，或反之）
3. **描述撰写质量**
   - 语句通顺，表达清晰完整
   - 是否出现了极其明显的过程及产物问题却偷懒没有写出
   - 是否真正看过了过程与产物
   - 是否定位到问题具体环节
   - 是否指出了具体行为/问题
   - 是否存在 AI 生成痕迹

## 五、其他常见问题

### 🛠️ 任务定义与轮次逻辑

**Q：数据提交是以“轮次”为单位吗？“一轮”的具体定义是什么？**

**A：**&#x662F;的。每一个单轮对话（Single-turn）即为一条独立的数据。

- 一轮 = 一次交互（用户提问 + 模型回答）。
- 即使是一个复杂的任务进行了多次对话，也需要拆分成多条数据提交。

**Q：任务类型是根据当前轮次确定的，还是整个对话确定的？**

**A：**&#x6839;据当前轮次确定。每一轮的标注都要基于该轮的实际内容。

- 示例：第一轮是“代码生成”，第二轮如果是修复第一轮的错误，则第二轮的任务类型应变更为“Bug 修复”。

### 🔄 截断与“继续”处理

**Q：对于用户输入了“继续”的轮次，数据应该如何提交？**

**A：**&#x5BF9;于出现了模型自己中断，后一轮需要人为输入“继续”的情况，两轮的人评其实是对同一个提示词的任务在做打分和评价，此时 Prompt、turnID/PromptID 都提交前一轮的，但打分和评价基于“继续”后的轮次（可能不止一次继续）来综合评价任务的完成情况，并且在【其他问题】中说明中断的情况。

**Q：对于“继续”后的轮次，评价标准是什么？**

**A：**&#x8BC4;价标准依然是上一轮用户希望模型完成的任务。

### ⚖️ 评分与验收标准

**Q：数据验收是针对整个多轮对话会话，还是单轮数据？**

**A：**&#x9488;对单轮进行验收，每一个单轮对话是一条数据。

**Q：如果模型前几轮翻车，但最后一轮修正了，这几轮该怎么评分？**

**A：**

1. **前几轮：**&#x901A;常应该会出现一些低分。
2. **最后一轮：**&#x9488;对这一轮的表现来评估，结合专家个人用户体验。
   - 如果这一轮依然是反复自纠、磕磕绊绊才完成，体感可能较差。
   - 如果是突然开智回到正轨、高效完成交付，即使前面轮次有错，最后一轮也可能出现高分甚至满分的情况。

**Q：是否可以接受多模态 Prompt？**

**A：**&#x6211;们可以接收多模态数据，如果是多模态，除了 prompt 之外还需要增加一个字段“prompt 附件”上传 prompt 中的附件，提交上会多一步的时间，不可以因此作为原因而提高 AHT，请内部衡量。

### 🎯 题目多样性与难度要求

**Q：对任务的难度上限和下限有要求吗？**

**A：**&#x8981;求如下：

- **上限：**&#x65E0;量化要求，欢迎高难度挑战。
- **下限：**&#x6709;严格限制。禁止提交过于简单的题目。

**Q：同一个 repo 可以出多少题目？**

**A：**&#x4E0D;限制，但是禁止雷同的 repo+雷同的题目（包括第一期的数据）。

**Q：什么样的题目是“过于简单的题目”？**

**A：**&#x540C;时满足下述两种及以上特征的题目，是过于简单的题目，拒收：

| 维度    | “过于简单”的特征                             |
| ----- | ------------------------------------- |
| 修改范围  | 单文件局部修改、纯函数级实现（典型如 LeetCode 题、独立工具函数） |
| 上下文依赖 | 不需要任何 Repo 上下文、纯文本 Prompt 就能完成        |
| 交互轮次  | 大多数模型 1 轮就能完美交付，不需要看报错、不需要规划          |
| 技术广度  | 单一文件、单一语言、不涉及前后端联调或跨服务                |

## *存档：如何写好不满意原因

> 💡 在提交不满意原因时，请先在脑海中问自己三个问题，想清楚：
>
> 1. “模型是从哪一步开始降智的？”
> 2. “模型的具体什么操作让我觉得很弱智？”
> 3. “换做是一个人类高级工程师，遇到这种情况会怎么做？”

### “不满意原因”的硬性要求（质检会看）

- 过程与产物都要分析，要分别说清“过程哪里差、产物哪里差”。
- 定位到具体环节和步骤：指明问题发生在哪个步骤、哪个工具调用、哪次文件改动。
- 用证据，不用形容词：引用报错信息、出错的文件名/函数、漏掉的具体需求；禁止只写“效果不好/不行/一般”等笼统的表面症状。
- 只能写由模型本身能力造成的问题，不能写环境/网络波动导致的问题，例如模型请求失败。

### 写作方法参考

> 💡 一条合格的原因必须同时具备三要素：
>
> - **触发节点（When）：**&#x5728;哪个阶段或哪个动作出了问题？
> - **实际行为（What）：**&#x6A21;型做错了什么？
> - **业务影响（Impact）：**&#x8FD9;个错误导致了什么后果？
>
> **一条好的原因，除此之外还需要能够指出模型错误行为的根因和正确做法。**
>
> 一条数据可能存在很多个问题点，每一点都应按三要素展开说明，写作格式无需完全一致（不作为质检点），但是上述硬性要求都需要踩到（作为质检点）。

可以参考的文本格式：

```text
过程问题：
在【第几步/哪个环节】，模型【做了什么具体行为】→ 导致【什么后果】（→ 【根因和正确做法】）

产物问题：
产物在【哪个文件/功能】存在【什么具体问题】，表现为【客观证据，如报错/缺失需求】，无法满足【哪条需求】。

产物问题可能是由过程问题导致的，这时可以是更为完整闭环的表述：
在【第几步/哪个环节】，模型【做了什么具体行为】→ 导致产物在【哪个文件/功能】存在【什么具体问题】，表现为【客观证据，如报错/缺失需求】，无法满足【哪条需求】（→【根因和正确做法】）。
```

### 找问题的方向

> 💡 **我们这里虽然给出了写作/找问题的方法作为参考，但是不能有ai文案的痕迹特征**

在读模型过程和产物时，我们需要关心的问题包括但不限于：

#### 1. 过程类常见问题

| 类别   | 典型表现                                                                                             |
| ---- | ------------------------------------------------------------------------------------------------ |
| 指令遵循 | 模型是否严格遵守了用户在 Prompt 中明确提出的所有约束条件（如：特定库的使用、代码风格、禁止修改的文件等）？是否存在忽略明确约束、漏做部分需求、做了没要求的额外改动、擅自改技术栈等行为？ |
| 任务规划 | 模型是否能合理拆解任务？是否有清晰的阶段性状态追踪？遇到歧义时是否主动求问？是否有阶段性总结或反馈？是否无规划/规划错误、步骤顺序混乱、目标漂移、来回反复？                   |
| 工具使用 | 模型是否能够调用合理的工具？是否出现了参数错误，改文件前不先读、同一失败调用反复重试、不会用搜索等问题？                                             |
| 幻觉   | 模型是否出现幻觉？是否编造看似合理、实则不存在的 API/参数/配置项，或臆造了 repo 里的文件/函数，声称做了实际没做的操作？                               |
| 验证缺失 | 模型是否没有执行合理的测试验证就说完成？是否对报错视而不见、不检查输出？                                                             |
| 纠错能力 | 模型陷入死循环、重复同一种无效修复、或者遇到困难就轻易放弃？                                                                   |
| 交互沟通 | 该问不问/不该问乱问、进度汇报误导、缺乏阶段性总结等。                                                                      |

#### 2. 产物类常见问题

| 类别      | 典型表现                        |
| ------- | --------------------------- |
| 正确性     | 编译/运行失败、逻辑错误、边界 case 挂、引入回归 |
| 完整性     | 漏需求、半成品、留 stub/TODO         |
| 代码质量    | 可读性差、无错误处理、结构差、违反 repo 规范   |
| 过度工程    | 无意义的高复杂度、多余文件               |
| 偷工减料/造假 | 硬编码、假数据、删/改测试来 hack、占位实现    |
| 破坏性     | 删改无关代码、破坏既有功能               |
| 安全      | 引入漏洞                        |
| UI/美观度  | 难看、与设计不符、布局错乱               |
